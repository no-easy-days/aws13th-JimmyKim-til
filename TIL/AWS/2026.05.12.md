## LLM 평가 방법

- 빠르게 후보를 간추리고, 사례 기반 벤치마킹 및 나만의 우선 순위 기반 선별을 통해 적합한 Foundation Model을 선택해야한다.
  - 우선 순위 : Latency / 품질 / 비용,  3가지 요소를 고려하여 선택하자.


- LLM 평가 vs RAG 평가
  - LLM 평가 : 다양한 태스크에 대한 기본 능력 평가 (모델 자체 능력), RAG 평가에 비해 비교적 간단하지만, 전문 영역
  - RAG 평가 : 생성된 응답 성능 평가 (전체 파이프라인), LLM 평가에 비해 과정은 조금 복잡하지만, 지표가 명확함
  

- RAGAS : RAG 시스템 전용 평가 프레임워크. **평가 샘플**, **평가 지표** 두가지 핵심 요소로 구성된다.
  - 평가 샘플 4요소 : 사용자 질문 / Knowledge Base로부터 불러온 컨텍스트 / Response / Reference 답변


- AI 검색 성능 평가의 핵심 지표

1. 컨텍스트 정밀도(Context Precision)
   - 검색 결과가 내 질문과 얼마나 연관이 있는가? 
2. 컨텍스트 재현율(Context Recall)
   - Knowledge Base에 있는 모든 관련 정보를 검토했는가? 누락 여부 확인
3. 컨텍스트 엔티티 재현율(Context Entity Recall)
   - 사용자의 질문에 언급된 구체적인 엔티티(사람, 장소, 제품 등)가 포함되어 있는가?
  
- LangChain : RAGAS와 Bedrock과 연결하는 중간 다리 역할. 

- AI 생성 평가의 핵심 지표

1. 노이즈 민감도(Noise Sensitivity)
   - 관련성 없는 텍스트가 잘 제거 되는가?
2. 응답 관련성(Response Relevancy)
   - 사용자 질문에 적합한 답변이 제공되는가?
3. 충실도(Faithfulness)
   - 답변이 컨텍스트를 기반으로 하는 내용이 맞나?

## Bedrock의 대표 특장점 & 기능

1. 프롬프트 캐싱 : API 호출 시 반복적인 컨텍스트를 캐싱할 수 있다. (비용 절감 효과)
2. 지능형 프롬프트 라우팅 : 프롬프트를 여러 Foundation Model로 자동 라우팅하여 최적 모델 선택 및 응답 품질을 최적화한다.
3. Latency 최적화된 Inference : `Optimized` 모델 채택을 통해 성능 향상할 수 있다. (조금 비쌈)

## Responsible AI

- 강제성은 없다. KPI 느낌. 한국의 경우 인공지능기본법률이 26년 1월 제정되어서 약간의 강제성이 부여되었다.
- 4가지 과제 : 할루시네이션 / 유해성 및 안정성 / 저작권 / 데이터 개인 정보 (원론적인 내용...)
- "편향"은 항상 경계해야하고, 프롬프트 인젝션 / 프롬프트 유출을 방지해야 한다.

### AWS Bedrock Guardrail

- AWS 제공 AI 보안 솔루션. BedRock 내에서 설정할 수 있다.
   - 사용자 입력 / Foundation Model 출력 두 단계에 대하여 주제, 특정 단어 및 콘텐츠 필터링, Auto-Reasoning 설정할 수 있다.
   - Auto-Reasoning : 자동 추론 검사. 사용자가 정의한 비즈니스 규칙, **"정책"**을 바탕으로 "응답이 논리적으로 맞는지"를 검증한다.

## ★★★AI Agent★★★

### 에이전트 구동 핵심 기술 : ①AI SW Integration ②CoT Inference ③Multi-Modal Inference ④Agent 개발 Framework


- Foundation Model이 뇌라고 하면, 팔~다리를 붙여주는 것이 Agent이다.
   - AI 소프트웨어 : 프로그램. 결국 그 안에 보면 Foundatiomn Model이 있다.
   - CoT : 보통 Foundation Model에 내장되어있긴 한데, 코드로 구현 가능하다. 얘가 있어야 에이전트를 만들수 있다.
   - 멀티 모달 : 하나의 에이전트가 여러가지 인풋 정보(텍스트, 이미지, 동영상 등등...)를 받아서 처리할 수 있다.
  
  
- 함수 호출 (tool use) 
   - Foundation Model의 결과값을 바탕으로 에이전틱 AI가 어떤 도구를 호출할지를 결정한다. **"Reasoning & Acting(ReAct)"**
   - RAG / 메모리 / 어플리케이션 실행 / 웹 네트워킹 / API / Guardrail 등의 도구를 호출하여 외부 시스템과 상호작용한다.
   - 결국 ReAct 에이전트도 CoT를 기반으로 단계적으로 동작한다. 


## MCP 서버(Model Context Server)
- 에이전틱 AI가 도구를 써야하는데,그 도구를 쓰려면 결국 에이전틱 AI도 사용법을 다 알아야 하기에 너무 복잡하다. 
- 도구 개발자도 에이전틱 AI가 활용할 수 있도록 고려해줘야 한다. 그래서 하나의 **"표준화"된 서버-클라이언트 아키텍쳐**로 만든 것.  
- 결론은 **에이전트가 어떤 도구를, 그 도구를 어떤 식으로 써야하는 지를 명시**한 규약.
  
  
### A2A
- Agent-to-Agent. **"에이전트끼리" 서로 상호 작용 및 통신시키는 규약**. 
- 예전엔 에이전트를 관리하는 Supervisor가 있었는데, 이제는 별도 제약없이 에이전트끼리 통신한다. 
- Agent 카드를 활용하여 에이전트 간 서로의 정보를 파악한다. (일종의 명함 느낌)

## Bedrock Agent

1. Bedrock Flows
  - AWS StepFunction과 유사(드래그&드랍 방식), 생성형 AI 관점에서 각종 에이전트들을 활용한 워크플로 정의.
  - 워크플로의 각 단계는 "노드"라고 칭하며, 이 노드들을 가지고 사용자만의 워크플로를 구현한다. (Console에서 클릭클릭)


2. Bedrock Agents
  - 각종 에이전트를 AWS 환경 내에서 만들어 내는 것. 
  - 일반적인 에이전트와 개념은 유사하지만, Bedrock에서 **"도구(tool)"** : **"Action Group"**이라 칭하고, `Lambda`가 기본!
  - 필요하다면, AWS OpenSearch 기반으로 구성한 Knowledge Base 를 활용.
  - 메모리 보존 기능 존재(Elasticache 또는 DynamoDB 안붙일 수 있다)
  - **제약 사항** : Bedrock에서 제공하는 Foundation Model"만" 사용 가능 / **다른 프레임워크(LangChain 등) 기반 에이전트 실행 불가**
 

### 3. Bedrock AgentCore
  - Bedrock Agent의 제약 사항을 해소하기 위해 출시됨. → ***"Any Foundation Model, Any FrameWork"***
  - 핵심 구성 요소
     - `Runtime` : 개발한 Agent를 AWS 환경에서 실행할 수 있는 환경. 기본적으로 Docker 컨테이너 기반.
   	 - ★`Identity`★ : Agent 구동을 위한 **도구 활용 권한** 및 자격 증명. **"Inbound~Outbound 인증"** 처리
 	 - `Browser` : AWS 제공 도구, 웹 사이트 탐색, 웹 기반 작업 환경 제공
	 - `Code Interpreter` : AWS 제공 도구, Agent 자체적으로 특정 코드를 실행될 수 있는 환경 제공
     - `Gateway` : 뒷단에 붙일 다양한 MCP를 일종의 API Gateway처럼 제공. 추가 기능으로 Sementic(유사성) 검색 지원.
	 - `Policy` : 도구 호출 및 사용성에 대한 정책 모음. `Gateway`와 연동 사용한다.
	 - `Memory` : 관련 컨텍스트를 담은 메모리(Sementic)를 제공하여 이전 상호 작용에 대한 학습 지원. 
	 - `Observability` : 모니터링 기능. Agent 실행 과정을 단계별로 시각화 및 대시보드
	 - `Evaluations` : `RAGAS`와 유사함. Agent의 동작에 대한 품질 평가 모듈
	
	
  > Bedrock Agent와 Bedrock AgentCore는 엄연히 다르다!
