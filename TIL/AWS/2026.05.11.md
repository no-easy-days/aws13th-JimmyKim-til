## 생성형 AI 개요

- 생성형 AI도 머신러닝의 한 유형 중에 하나이다. AI > ML > DL > Generative AI 구조로 상위~하위 집합 형태. (강의 자료 참조)

#### *"새로운 콘텐츠 및 아이디어를 생성하는 사전 훈련된(★Pre-Trained★) "대규모 모델"(★★★Foundation Model★★★)"*

`Machine Learning Model` : 지도 학습 기반. 특정 기능에만 특화되어 있기 때문에 자체적인 알고리즘에 의해 분석을 진행한다. <br>
`Foundation Model` : 비지도 학습 기반. 레이블이 지정되어 있지 않은 모든 것들을 다 받아들이며, **"프롬프트"** 가 없으면 뭘 해야하는 지를 모른다. <br>
  - LLM : Attention(문맥을 이해하는 알고리즘)과 Transformer(Attention 알고리즘 기반으로 동작하는 "병렬" 처리)를 통해 획기적인 발전이 이루어졌다. 
`Context` : 모델 출력을 조정하기 위한 추가/외부 정보(RAG, Agent 등) <br>
`Inference`(추론) : 프롬프트와 컨텍스트를 입력으로 사용하여 Foundation Model을 호출하고 응답을 출력으로 가져오는 프로세스.

## 생성형 AI 프로젝트 프로세스

1. 범위 정의(고객 요구 사항 이해, 조직 역량 고려)
2. 데이터 및 모델 선택(기업 데이터 식별 및 Pre-Trained 모델 선택)
3. 모델 적응(프롬프트 엔지니어링, 증강, 에이전트 적용)
4. 모델 사용(성능 및 변화를 지속 모니터링 및 추적 관리)


※ 이번 교육에서 사용할 어플리케이션 아키텍쳐


- Application FrontEnd(S3) → Application Logic(API Gateway & Lambda) → **Foundation Modeel Interface(Bedrock)** → Foundation Model


- LLM(Foundation Model) 요청에 대한 구성 요소 : 입력 컨텐츠(What), 페르소나 & 행동지침(How), 컨텍스트 & 외부 리소스(Tool), 추론 파라미터(Fine-tuning)
  - 추론 파라미터 : 결정성(Temperature, Top-p) / 토큰 수 / Stop Sequence / 응답 갯수 / 패널티(일부 모델만 지원)
    - Top-p : 랜덤성을 제어하는 파라미터. 가장 확률이 높은 "범위를 지정". 일관성이 중요하다면 Top-p를 낮춰야 한다.
	- Temperature : Top-p 안에서의 랜덤성. 창의성이 중요하다면 Temperature를 높일 수록 랜덤성이 부여된다.
  - 이미지 추론 파라미터 : Prompt Strength(cfg_scale) / Generation Step(steps) / Seed
    - Prompt Strength : 내가 넣은 프롬프트를 얼마나 잘 지킬 것인가. 창의성이 중요하다면 Prompt Strength를 
	- Generation Step : 이미지가 샘플링되는 횟수를 결정. 높이면 높일수록 시간은 많이 걸리지만 퀄리티는 높아진다.
    - Seed : 배경화면. Seed 넘버를 바꿔가면서 원하는 배경화면을 고르면 된다.

### Amazon Bedrock

- ***API를 기반***으로 250개 이상의 ***Foundation Model을 선택하여 사용***할 수 있는 인터페이스
- bedrock : 제어 영역, 관리 및 구성 작업 처리 (대표 API : ListFoundationModel)
- bedrock-runtime : 데이터 영역, Foundation Model 정의 및 각종 상호 작용 로직 처리 (대표 API : InvokeModel, Converse)
  - InvokeModel : 특정 Foundation Model을 쓰겠다고 하면, ***각 모델에 정해진 포맷에 맞춰서 Payload(Body)를 정의***해야함.
  - **Converse(추천)** : 모델에 정해진 **포맷을 고려하지 않아도 된다**. 코드를 변경하지 않고 모델 변경 가능! (Bedrock답게 사용하는 API)

## 프롬프트 엔지니어링

- 프롬프트를 좀 더 잘 써보자는 것이 프롬프트 엔지니어링이다.
- Foundation Model 가장 큰 문제점 : Hallucination, Knowledge Cutoff(최근 정보 알지 못함)
  > 해결 방법 ?
  >> Foundation Model 자체 훈련 / 모델 Fine-Tuning   →   기업에서 이 두 방식은 더 이상 사용하지 않는다. 비싸니까. ROI가 안나옴
  >> ★★★Agent★★★(추론과 액션을 통한 특정 작업 수행) / ★검색 증강 생성(RAG)★ / 프롬프트 엔지니어링
  

- 프롬프트의 구성 요소 : 지침 & 컨텍스트 & 입력 데이터
- **모델의 응답 평가 기준**
  - HITL(Human In The Loop) : 사람이 검토를 진행해서 적합성과 품질을 확인
  - LLM-as-a-Judge : Foundation Model을 통해 얻은 결과를 "다른 Foundation Model"을 통해 검증
  
  
### 프롬프트 기법
  - Zero-Shot : 예시 없이 물어보는 기법.
  - Few-Shot : 예시 몇가지를 제시해서 물어보는 기법. (HITL이랑 유사함)
  - **★CoT(Chain-Of-Thought)★** : Foundation Model은 계산(논리적 사고)을 잘 못한다. 최근 버전 모델들은 CoT를 내장시켜서 나옴.
    > 내장되어 있지 않다면, Think-Step-By-Step 이라는 마법의 명령어를 넣어서 조금 개선된 결과를 얻을 수 있다!



### 프롬프트 모범 사례
  1. ***구체적이고 명확하게 작성, 역할(페르소나) 작성, 명확한 구분 기호(따옴표)가 있는 구조 사용, 제약 조건 및 출력 서식을 포함해라.***
  2. 프롬프트 템플릿(개발자가 정의) 사용해라.
  3. 쿼리를 분해해라. (쉽게 이야기하면 쪼개라)

## Amazon Bedrock API 활용 방법

- Inference Mode 선택 : Batch(대량 데이터를 한번에 핸들링할 때) / On-Demand(Default) / Provisioned(미리 확보해두는 개념. MU 기반)
  - On-Demand : (Input Token X 모델 별 입력 토큰 가격) + (Output Token X 모델 별 출력 토큰 가격)
  - Batch : S3 Bucket과 연동해서 사용하며, `jsonl` 형태로 작업을 정의한다. 생성 시 바로 실행됨.
  - Prompt Caching : `Claude`, `Nova` 모델만 사용 가능하며, 말그대로 캐싱을 위한 `CachePoint` 를 잡아서 반복 컨텍스트 처리에 특화  
- **★Inference Profile★** 사용 : 추론 프로파일. "특정 리전"에 있는 Bedrock을 사용한다. 가용성 고려.

- 텍스트 요약 기법 : 추출(전체 문서에서 중요 문장 그대로 뽑아냄) / 추상(원문 이해 후 새로운 문장으로 다시 씀)

- 단기 메모리(ElastiCache) / 장기 메모리(DynamoDB)로 구분하고, 필요에 따라 Lambda 등을 활용해서 구분 호출한다.

## RAG
- "Retrieval Augmentation Generation." 어딘가에서 끄집어온 데이터를 가지고 프롬프트를 보강해서 Foundation Model을 호출하는 것. 
- Foundation Model의 제약 사항 & 문제점때문에 등장한 개념. 특정 도메인 정보를 알지 못하는 한계가 존재하기 때문에, 이에 대한 해결책.
- RAG를 구현하기 위해서는 모든 데이터를 ***"벡터" 데이터베이스*** 방식으로 저장해야 하며, 그 저장소를 **Knowledge Base**라고 칭한다.
- Knowledge Base 구성(**하이드레이션**) 절차 ~ "Chunking " -> "Tokenization" -> "Embedding"


  1. 기업 데이터 소스를 청크(Chunk) 단위로 분할
    - Chunking 전략 : Fixed Size / Semantic / Hierachical. -> 전략을 어떤걸 선택하는지에 따라 결과물이 달라진다. 

  2. 청크를 임베딩으로 변환
    - Tokenize(Foundation Model 자체적으로 결정함)를 통해 Token으로 변환되고, 그 Token을 Embedding한다.
    - Embedding : 자연어를 기계가 이해할 수 있도록 **숫자** 형태인 **"벡터"**로 바꾸는 일련의 과정
      > 왜 벡터로 저장해야하는가 ?
      >> "거리 계산". 유사성을 계산할 수 있게 된다. Foundation Model은 가장 유사한 걸 찾는 모델이니까!!


  3. 임베딩 데이터를 Knowledge Base에 저장
    - 벡터 저장소(기본값) : 구조화되지 않은 일반 텍스트를 사용하여 **유사성 기반 검색**을 빠르게 진행해야할 때 사용.
	- 그래프 데이터베이스 : 데이터를 노드(Node) 와 엣지(Edge) 로 표현해서, **연결 관계**(relationship)를 탐색하는 데 최적화.
	- 하이브리드 : 벡터 저장소의 유사성 기반 검색의 한계를 보완하기 위해 **"키워드" 검색**을 추가한 유형.

  
- Knowledge Base 설정 완료 후, "Agent(또는 Orchestrator) Layer"에서 어플리케이션이 Knowledge Base로부터 데이터를 꺼내오는 방식을 설정한다.
- 사용자가 쿼리 전송 시 Tokenize 및 임베딩 처리되고, Orchestrator Layer에서 **임베딩된 쿼리와 Knowledge Base에 임베딩 간의 유사성 검색**을 수행한다. 
- 컨텍스트 및 사용자 입력을 토대로 증강된 프롬프트를 생성하며, 그 프롬프트를 바탕으로 Foundation Model에서 LLM 응답을 생성한다.


- AWS 에서는 ***"Bedrock Knowledge Base"*** 기능으로 RAG를 구현 및 활용할 수 있다.
  - 작동 방식은 Chunking ~ Tokenization ~ Embedding ~ KnowledgeBase 저장으로 이뤄지는 프로세스는 완전 동일하다.
    > 기업 데이터 소스와 Knowledge Base의 동기화(Sync)가 핵심! 얼마나 자주할 것인지, 수동 or 자동으로 할 것인지가 Point.
	>> Sync가 Console에서 했다면, 코드 레벨에서는 StartIngestionJob을 통해 데이터 동기화를 수행한다!


  - Bedrock Knowledge Base에서 정보를 검색하는데 사용되는 API 종류
    - Retrive : 검색과 생성이 분리되어 있다. 쪼개진 일련의 작업을 `LangChain`과 연동하여 체인을 구성하여 연결한다.
      - LangChain : LLM 활용 어플리케이션 개발용 오픈소스 프레임워크. 말 그대로 `Chain` 이라는 걸 선언하여 파이프 라인을 통해 연결하는 구조.
    - RetriveAndGenerative : 한번의 API 호출을 통해 검색과 생성을 자동 처리한다. `LangChain` 필요 없음.
    - GenerateQuery : 자연어 사용자 쿼리를 구조화된 데이터 저장소에 적합한 형식의 쿼리로 변환.
